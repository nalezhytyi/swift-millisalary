# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Millisalary, the app that shows your salary being earned in real time, rewritten natively in Swift for macOS. It replaces the Electron + React app in `../electron-millisalary` (~273 MB, most of it the Electron framework, and most of its UI work went into faking macOS controls in CSS). That app's `CLAUDE.md` is the behaviour spec: what isn't ported yet is described there. Treat `../electron-millisalary` as a read-only reference: never edit, build or commit there (reading it, or bundling its TypeScript into a temporary folder as the parity script does, is fine).

The user writes in Ukrainian: answer in Ukrainian. Code, comments, commit messages and this file stay in English.

## Commands

```bash
xcodegen generate                       # (re)generate Millisalary.xcodeproj from project.yml; after adding files too
xcodebuild -project Millisalary.xcodeproj -scheme Millisalary -derivedDataPath build/DerivedData build
xcodebuild -project Millisalary.xcodeproj -scheme Millisalary -derivedDataPath build/DerivedData test
swift test --package-path Packages/MillisalaryCore   # the same tests without Xcode, in seconds
open build/DerivedData/Build/Products/Debug/Millisalary.app
scripts/parity/generate-fixtures.sh     # regenerate the parity fixture from the Electron app's TypeScript
swift scripts/generate-icons.swift      # regenerate AppIcon in the asset catalog from MoneyFace.png
swift scripts/check-localizations.swift [build/DerivedData]   # every text translated; with a build, every text the code uses cataloged (Localization)
scripts/build-dmg.sh                    # the universal Release app packed into build/Millisalary-<version>.dmg
scripts/release.sh                      # build the dmg and PUBLISH it as a GitHub release
```

- XcodeGen (`brew install xcodegen`, 2.46) is required: `Millisalary.xcodeproj` and `Millisalary/Info.plist` are generated and gitignored, `project.yml` is the source of truth (build settings, Info.plist keys, the package dependency, the scheme). Files in `Millisalary/` are picked up by folder, but only after `xcodegen generate`.
- Release: `-configuration Release`; the app is in `build/DerivedData/Build/Products/Release/` (8.2 MB on 2026-11-01, down from 13 MB: the executable 3.7 MB, about 1.4 MB of it Amplitude-Swift's code; `AmplitudeCore.framework` 1.8 MB, a prebuilt binary signed by Amplitude, which Xcode won't strip; `Assets.car` 1.4 MB, nearly all the icon; the face's animation 0.93 MB and the flying money 0.52 MB; the Release link warns once about an ambiguous atom inside a dependency's own code). Release sets `DEPLOYMENT_POSTPROCESSING = YES`, without which a plain `build` doesn't strip (only an archive does): the symbol table was 4.8 MB of the 8.5 MB executable. The dSYM is made before the strip, so crash logs can still be symbolicated with it. Release also compiles with `-Osize`, about 100 KB less code; the CPU time goes to SwiftUI, not the app's own code. It's universal (arm64 and x86_64: Xcode's default `ARCHS_STANDARD` with `ONLY_ACTIVE_ARCH = NO` for Release; `build-dmg.sh` builds for `generic/platform=macOS` and checks with `lipo`). `build-dmg.sh` makes a 4 MB dmg with the app and an Applications link (`hdiutil`, HFS+, ULMO: LZMA, readable since macOS 10.15; zlib's UDZO made it 5.1 MB), after `codesign --verify --deep --strict` and after starting the executable with `--smoke-test` under a 20 s alarm: `main.swift` exits there before any app code runs (no settings or window), so it only proves that dyld loads the binary and every framework it links, which 0.1.0's didn't. It starts this Mac's architecture only (the x86_64 slice would need Rosetta).
- Before publishing, launch the Release app once (installing the dmg into /Applications, with the user's go-ahead: it's their real settings domain). `build-dmg.sh`'s `--smoke-test` only proves that dyld accepts the signature and the frameworks; nothing else runs the Release app's own code (0.1.0 crashed at launch because nobody had started it).
- Never run `scripts/release.sh` without the user's explicit approval for that specific release: `gh release create` publishes. It refuses a dirty tree, a missing `origin` or one other than `https://github.com/<repo>`, `git@github.com:<repo>` or `ssh://git@github.com/<repo>` (each with or without `.git`, `<repo>` being `MillisalaryReleasesRepo`), a `gh` account other than the repo's owner (run it as `GH_TOKEN="$(gh auth token --user nalezhytyi)" scripts/release.sh`), an existing tag and an unpushed HEAD, then tags `v<MARKETING_VERSION>` on HEAD and uploads the dmg with generated notes. Bump `MARKETING_VERSION` in `project.yml` first: it's the app's version (`CFBundleShortVersionString`) and the update check compares it with the latest tag. The README tells users how to open the unsigned app.
- Commit with the repo-local git identity (`nalezhytyi`, set in `.git/config`), not the global work identity. Conventional Commits with a lowercase scope, e.g. `feat(tray): …`, `feat(windows): …`, `fix(core): …`.
- `origin` is `github.com/nalezhytyi/swift-millisalary`, public (created 2026-11-01 at the user's go-ahead). Never push or release without the user's explicit approval for that specific action. Git and `gh` act as `nalezhytyi` without switching the active `gh` account, which is a work one: the repo-local `credential.https://github.com.helper` gives git `gh auth token --user nalezhytyi` (as in the Electron repo), and `gh` commands run with `GH_TOKEN="$(gh auth token --user nalezhytyi)"`.

## Structure

- `Packages/MillisalaryCore/` — a local Swift package with everything that doesn't need AppKit or SwiftUI: the earnings model, settings schema, validation and edits, money formatting, the menu bar's text. Pure and unit-tested; the app depends on it (`packages:` in `project.yml`), and the scheme's test action runs its tests.
  - `Earnings.swift` — `EarningsModel` (`calculations.ts`): `earnings(at:_:)`, `workingWindow(on:_:)`, `isScheduledDay(_:workingDays:)`, `paydayInMonth(of:payday:)`, `nextPayday(from:payday:)`, plus `Period` (with `label`, "This hour" … "This year", the menu bar's and Breakdown's names), `EarningsSettings`, `WorkdaySettings`, `EarningsSnapshot`.
  - `Settings.swift` — `Settings` (`settings.ts`): the same 15 keys, values and defaults as the Electron app's `settings.json`, plus this app's own `dialFacts` (since 2026-11-01: the `DialFact`s in the card under the Earnings dial, an array of their names; the validator keeps the known names, each once, the first four, so a later version's facts are dropped, and `[]` hides the card); `Settings(sanitizing:)` / `applying(_:)` / `apply(_:for:)` are `sanitizeSettings` / `sanitizePatch` / one validator, `propertyList` is the way back, `workday` / `earningsSettings(exchangeRate:)` feed the model.
  - `SettingsEditing.swift` — the settings pane's edits with the coupled schedule fields (`settingsDraft.ts` and the `getNext*` helpers): `setStartHour` moves End by hours a day, `setEndHour` recomputes hours a day (an End before Start pulls Start back to it, and with no time between them hours a day fall back to 8, as in the Electron app), `setWorkingHoursPerDay` moves End, `setWorkingDays` / `setPayday` normalize.
  - `SalaryForm.swift` — `normalizeWorkingDays`, `normalizePayday`, `normalizeWorkingHoursPerDay`, `endHour(from:workingHoursPerDay:)` (`getEndHourFromStart`), `workingHoursPerDay(from:to:)` (`calculateWorkingHoursPerDayValue`), the defaults (8 hours, 22 days), and `salaryInput(_:locale:)`, what the salary field keeps of an edit.

Read byte by byte, not with a Swift `Regex`: the settings parse both times on every tick of the window, and the regex cost more than the earnings model (the validators check times and currency codes the same way).

  - `Notifications.swift` — `EarningsModel.scheduledNotifications(around:settings:)` (`getScheduledNotifications`: the end of yesterday's and today's paid working windows, payday at the start time, keyed `end_of_day:2026-10-29` / `payday:…`), `NotificationTiming.due` (`check()`: once per key, a late one still sent for 3 h, the last 10 handled keys kept; with `previouslyScheduled`, one that a settings change made due is only marked) and `NotificationContent` (Workday complete / It's payday).

## The port and its parity

The Swift core must give the Electron app's results, so the TypeScript is the oracle. `generate-fixtures.sh` bundles `fixtures.ts` with the esbuild in `../electron-millisalary/node_modules/.pnpm/esbuild@*/` (aliasing `@shared` and `@renderer` to its `src/shared` and `src/renderer/src`, resolving `dayjs` from its `node_modules`) into a temporary folder and runs it with node. The fixture holds 2610 `calculateEarnings` / `getWorkingWindow` / `isScheduledDay` results (15 schedules: overnight, no end time, same start and end, fractional hours and days, 24-hour days, a rate, no salary; at edge instants plus 20 seeded random ones over 2026–2028; in Europe/Kyiv, America/New_York and Asia/Kolkata), every payday 1–31 for 13 months, 256 `formatCurrency` and 256 `formatCurrencyParts` results (8 currencies, 2 and 4 digits, half-way amounts), 174 coupled-field edits (`withStartHour` / `withEndHour` / `withWorkingHoursPerDay` / `withWorkingDays` / `withPayday` on 6 schedules, times anchored to a day without a DST change), 176 `getScheduledNotifications` results (8 settings, 11 instants, Kyiv and New York), the normalizers (NaN and the infinities included), time strings and 22 raw settings objects through `sanitizeSettings`. `ParityTests.swift` compares money **exactly**, not with a tolerance. The fixture is committed, so the tests don't need node; regenerate it only when the reference changes, and keep the edge cases.

What makes the results equal to the bit, keep it when changing the core:

- Times are whole milliseconds as `Double`, like a JS `Date` (`epochMilliseconds`); `earnings(at:)` rounds `now` to a millisecond first. The arithmetic runs in the TypeScript's order (`millisecondSalary * 3600 * 1000`, not `* 3_600_000`).
- Each dayjs call maps to a `Calendar` call in the model's calendar (its time zone stands in for the local one): `startOf('day' | 'month' | 'hour')`, `add(n, 'day')` keeps the wall-clock time, `day()` is 0 for Sunday, `diff(…, 'day')` corrects for a change of UTC offset and truncates.
- `EarningsModel()` makes that calendar Gregorian, as a JS Date always is, in `TimeZone.autoupdatingCurrent`; not `Calendar.autoupdatingCurrent`, which is the calendar chosen in Language & Region, whose Hebrew, Islamic or Persian months would move the paid days, payday and the notification keys (`-AppleLocale 'en_US@calendar=hebrew'` tries one in a single process). The parity tests build their own Gregorian calendars; `CalendarTests` covers the default. Make a model when it's needed rather than keeping one: on macOS 27 the calendar follows a change of time zone (checked with `TZ` and `NSTimeZone.resetSystemTimeZone()`), but on macOS 14 it is ICU's and may keep the zone it was made in (not checked).
- `atMinutes` mirrors `startOf('day').hour(h).minute(m)`: the hour can run past 23 into the next day (a missing end time is start + hours/day, e.g. 20:00 + 9.5 h is 05:30 next morning) and fractional minutes are truncated (09:00 + 8.33 h ends at 17:19, not 17:19:48). When the end isn't after the start, the end is start + hours/day in milliseconds, truncated like a JS `Date`. `endHour(from:)` adds the same truncated milliseconds.
- `workingDays` is a `Double` and stays fractional (the Electron validator doesn't round it); `payday` is an `Int` (it does).
- `formatCurrency` rounds half away from zero (`.toNearestOrAwayFromZero`), as `Intl.NumberFormat` does; Foundation's default is half-even. Both format the shortest decimal of the double, so `1.005` gives `1,01`.
- The validators treat an `NSNumber` boolean as not a number and a number as not a boolean (`CFBooleanGetTypeID`), like `typeof`.
- Read JSON numbers with `JSONDecoder`, not `JSONSerialization`: the latter returns long decimals as `NSDecimalNumber`, whose `doubleValue` is off in the last bits (it broke the first test run). The Electron import has to take untyped JSON for the validator, so it converts any `NSDecimalNumber` through its exact text.
- Not covered: a start or end time inside a DST gap or overlap (03:00–04:00 in Kyiv on the last Sundays of March and October). JS moves a missing local time forward and picks the first of a repeated one; `Calendar` may differ. Those are Sundays, which aren't paid, so only `rates` could differ. The coupled fields are wall-clock in Swift, where the Electron app adds hours to a `Date` of today, so on a DST day its End could come out an hour off; the Swift one doesn't.

## Decisions

Taken on 2026-10-31 and 2026-11-01; "the user's choice" marks what the user picked between options.

- **XcodeGen** over a hand-made `.xcodeproj` or SwiftPM with a bundling script (the user's choice): a readable, diffable spec that `xcodebuild` builds, with asset catalogs, Info.plist keys and SPM dependencies (Sparkle later) handled by Xcode.
- **macOS 14** deployment target (the user's choice): `@Observable`, `SettingsLink`, `SMAppService`, `MenuBarExtra`, `@Environment` with observable types. Newer APIs (Liquid Glass, `glassEffect`, `toolbarBackgroundVisibility`, macOS 15/26) go behind `if #available`; on newer systems the native look comes by itself. Built with Xcode 27.2 / macOS 27.2 SDK / Swift 6.4.
- **Swift Testing** for tests. Swift 6 language mode; the app target uses `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` and approachable concurrency, so app code is main-actor by default (`DefaultsObserver` opts out with `nonisolated`). The core's `Settings` clashes with SwiftUI's `Settings` scene: write `MillisalaryCore.Settings` in SwiftUI files.
- **Bundle IDs**: Release is `com.nalezhytyi.millisalary`, the Electron app's, so the native app is its successor (same login item and notification identity, installs over it). Debug is `com.nalezhytyi.millisalary.debug`, so a dev build never shares settings, notifications or the login item with an installed copy, and it's named "Millisalary Dev" (`APP_DISPLAY_NAME`, `CFBundleName` and `CFBundleDisplayName`): with both called Millisalary, the user allowed notifications for the installed one in System Settings instead of the dev build (2026-11-01).
- **Signing**: ad hoc (`CODE_SIGN_IDENTITY = -`), not notarized, and without the hardened runtime (as in the Electron app); there is no Developer ID. Release 0.1.0 shipped with the hardened runtime on and crashed at launch for everyone: library validation only loads frameworks signed by Apple or the same Team ID, an ad hoc signature has none, so dyld refused the frameworks the app links ("mapping process and mapped file (non-platform) have different Team IDs"). Debug builds never had the hardened runtime, which is why testing missed it; `build-dmg.sh` now refuses that combination, and 0.1.1 fixed it. It also starts the built executable with `--smoke-test`, which catches any launch failure in dyld; the hardened-runtime check stays, since it names the cause and still holds on a Mac whose library validation is off. Not sandboxed, like the Electron app (no App Store, and a sandbox would keep the app from reading the Electron app's `settings.json`).
- **Settings in UserDefaults**, one value per key under the `settings.json` names, rather than a JSON file: native, inspectable with `defaults read`, editable with `defaults write`. Everything read goes through the ported validator, every edit through `SettingsStore.update`.
- **The main window is a SwiftUI `Window` scene**, not an AppKit `NSWindow` hosting SwiftUI. The hosted version was built first and dropped the same day: with `NSHostingController` (even with `sceneBridgingOptions = .all`) the `NavigationSplitView` got no toolbar, no sidebar button and no navigation title, and the sidebar drew the old flat way. In a `Window` scene macOS 27 draws it natively: the title is the selected row's name, the sidebar button is the glass circle next to the traffic lights. The cost: AppKit code can't open a scene, so `AppCommands` hands its `@Environment(\.openWindow)` to `AppController.openWindow` while the commands are built (at launch, window open or not), and `show(_:)` calls it, which opens the window or brings it to the front. Closing the window closes it (SwiftUI keeps the `NSWindow` and reuses it), unlike the Electron app's hide-on-close: a native window is cheap to bring back, and nothing ticks while it's closed. `NSWindow.allowsAutomaticWindowTabbing = false`: one window, no tab items in the menus.
- **Ukrainian, chosen by macOS** (2026-11-01; the user's choices: the language as macOS picks it rather than a picker in Settings, the whole interface, dates in the app's language): `CFBundleLocalizations` is `[en, uk]`, so the system's preferred languages or System Settings > General > Language & Region > Applications decide, and an English-first Mac sees no change. Money stays `uk_UA` in both languages (`54 321,00 ₴`: the parity fixture). See Localization.
- **Always in the Dock** (the user's choice), like the Electron app: closing the window leaves the app in the Dock and the menu bar; a Dock click or a second launch reopens it (`applicationShouldHandleReopen`, which always calls `show()`, so it also brings the main window back when only Settings is open). `showInMenuBar` hides the menu bar item (`isVisible`).
- **Settings is a window of its own** (⌘,; the user's choice on 2026-11-01, option D of four on the redesign canvas, over a segmented control in the pane, an overview with a page per group and pages in the sidebar; until then a pane in the main window's sidebar, which had grown too long): SwiftUI's `Settings` scene with a `TabView`, so macOS draws the tabs as toolbar icons and titles the window after the selected one. Five tabs: General (Open at login, Menu bar, Appearance), Pay (Salary and Payday), Schedule, At a Glance and Notifications; it opens on General, then on the last tab while the app runs (`Navigation.settingsTab`). Each tab is a grouped `Form` that is `.scrollDisabled` and `.fixedSize(horizontal: false, vertical: true)` at 500 pt wide, so the window takes each tab's height; in such a Form a `DatePicker`'s label rose 4 pt above the field's centre in a taller row (also in `LabeledContent`, and with the picker's height pinned), so Start and End are an `HStack` of a `Text` and the picker with its label hidden (`timeRow`). With a `Settings` scene SwiftUI adds its own Settings… item to the app menu, and with `AppCommands` on the main `Window` scene its `CommandGroup(replacing: .appSettings)` only added a second one; on the `Settings` scene it replaces it. AppKit code opens the window with the `openSettings` action `AppCommands` hands to `AppController` (like `openWindow`), the setup form with its own.
- **Settings shows only what works** (the user's choice), which since 2026-11-01 is everything the Electron app had: Salary (amount, salary and display currency), Schedule, Payday, General (Open at login), Notifications, Menu bar, At a Glance (this app's own, 2026-11-01, named by the user over "Under the dial" and "Dial widgets", which would read as macOS widgets: a preview of the card under the Earnings dial, then every `DialFact` with a checkbox and what it says; not live, worked out when the pane shows, when the settings or the rate change and once a minute (`SettingsFigures`, a `TimelineView(.everyMinute)`, so earned today and the days to payday don't go stale): on the window's 100 ms ticks every row worked the earnings out ten times a second and Settings went from 1.5% of a core to 17%, and a 1 s `TimelineView` for the changing ones still cost 2 to 3%; static it's 2% with the section on screen, Debug build, measured with `top -l 11 -s 1 -pid` against the previous commit built in a temporary worktree; the chosen ones first in their order with a `line.3.horizontal` grip; up to four, the others disabled at four; a checked row is dragged (`onDrag`) as the app's own `com.nalezhytyi.millisalary.dial-fact` type, declared under `UTExportedTypeDeclarations` in project.yml and registered with `.ownProcess` visibility, so other apps' text isn't taken and none is given; every row is an `onDrop` for that type that puts the dragged fact before it; Move Up and Move Down in a checked row's context menu and as accessibility actions reorder without a drag, or after the chosen ones when dropped on an unchosen one, with a 2 pt accent line over the row it would land before; drag and drop rather than `onMove`, which a grouped `Form` doesn't promise), Appearance. Native controls throughout (a grouped `Form`, `Picker` pop-ups with the current value added when it isn't a choice, e.g. 8.33 hours, `DatePicker` hour-and-minute fields on a fixed day without DST, a bordered salary field (`.roundedBorder`, 150 pt, right-aligned, as in the setup form, since 2026-11-01; before that the Form's borderless inline one) that commits on Return, when focus leaves or when the pane goes away, as native fields do, rather than on every keystroke like the Electron one, and then shows the stored salary again, so an amount the validator rejects or text that doesn't parse snaps back: a `TextField(value:format:)` kept showing it, since the stored value it reads hadn't changed. While typing it takes only digits, spaces and the locale's separators, with one decimal separator, as a number field's formatter does: anything else (a minus, a letter) is undone with a beep, and a "." or "," that isn't the locale's grouping separator becomes its decimal one. Foundation's number parse is lenient, it reads up to the first character it doesn't expect: in uk_UA "12a" was 12 and "54321.50" was 54321).

Releases go to `nalezhytyi/swift-millisalary` (`MillisalaryReleasesRepo` in `project.yml`), public so the update check can read them without signing in. One universal dmg rather than the Electron app's one per architecture: the native binary is small.

## Exchange rate

`ExchangeRateStore` (exchangeRate.ts in the Electron app). `follow(pair)` runs at launch and whenever a currency changes (an `withObservationTracking` loop in `AppController`; other setting changes don't refetch): the same currency is always 1; otherwise the cached rate for the pair at once (nil when there is none) and a fetch of `https://api.exchangerate-api.com/v4/latest/<FROM>` with `URLSession`, whose `rates[<TO>]` must be a finite number above 0, and a non-2xx status is a failure too. One `Task` per pair loops: after a fresh rate it sleeps 6 h, after a failure 1 min, doubling up to 30 min; following another pair cancels it, and a result for a pair no longer followed is dropped. `refresh()` on `NSWorkspace.didWakeNotification` fetches again at once. Each fresh rate is cached in the defaults as `exchangeRates`, a dictionary of `Double`s keyed like "USD>UAH" (read through `sanitizeRates`), so an offline launch keeps converting. `rate(for:)` only returns the followed pair's rate. Fetches and failures are logged under the `exchange-rate` category of the bundle ID's subsystem (no amounts, only pairs and rates). A request cancelled by following another pair or by a refresh (URLSession throws `URLError(.cancelled)`) ends quietly, with no error and no retry.

## Face and splash

`FrameAnimation.moneyFace()` (owned by `AppController`, in the environment as `FrameAnimation`) holds the frames of `money-face.webp`, decoded with ImageIO at the largest size a face is shown at (the splash's 96 pt × the scale of the sharpest screen attached, not the main one's, so a window on a Retina screen is sharp with a 1x display as the main screen: 192 px, about 20 MB, 0.2 s), and one clock (`epoch`): every `MoneyFace` plays the frames as a discrete `CAKeyframeAnimation` on its layer's `contents`, whose `beginTime` is the epoch (`CACurrentMediaTime()`), so frame `elapsed / 20 ms mod 150` shows on every face at once: the splash's face and the dial's show the same frame, which is how the browser's one clock per image behaved in the Electron app. The render server flips the frames, so a playing face costs the app nothing per frame: until 2026-11-01 a `TimelineView(.animation)` swapped a SwiftUI `Image` 50 times a second, which updated the window's view graph (and its layout) each time, and kept running with the screen off (see Performance). `restart()` (the splash, and the end of the decode) moves the epoch, and each face puts its animation back on from it. ImageIO's own player (`CGAnimateImageDataWithBlock`) does play WebP but took 3.7 s for the 3 s cycle, hence the own clock. `MainView` loads the frames when the window appears and drops them when it closes; frame 0 is decoded at once and the rest in the background. Until they're ready a face shows frame 0, not `MoneyFace.png`: the still picture is a different, glossier drawing (the animation is a cartoon one, smaller in its square), so switching from it would jump. `isLoaded` turns on once the background decode returns any frames, and the cycle runs over the frames it produced, so a frame that fails to decode is skipped rather than keeping every face on frame 0 and the splash on its 5 s timeout. Under Reduce Motion `MoneyFace` is the still picture, as the Electron app's `<picture>` was. Breakdown's payday card no longer shows the face: it plays its own `FrameAnimation.flyingMoney()` (a `@State` of `BreakdownView`, loaded on appear and dropped on disappear, on a clock of its own). Memory (`footprint`): 35 MB with only the menu bar item, about 55 to 60 MB with the window open on Earnings and 66 to 70 MB on Breakdown (optimized build, 2026-11-01; it depends on the main display, see Performance).

The splash (`SplashModel`, splash.ts in the Electron app) is an overlay over the whole `NavigationSplitView`, sidebar and toolbar included, in the detail pane's colour (`textBackgroundColor`: white, or #1e1e1e dark), with the face at 96 pt in the middle. Once every frame is decoded it restarts the face's clock and plays one 3 s cycle (a click skips the rest); then, if the window is on an Earnings pane and the dial's face (or, with no salary, the setup form's face, which reports the same way) has reported its frame (within 2 s), the face flies onto it in 0.5 s on `timingCurve(0.32, 0.72, 0, 1)` while the background fades out in 0.3 s, and the dial's own face, hidden until then, takes over on the same frame. Otherwise (Breakdown, no dial) and under Reduce Motion (the still face for 0.8 s) the splash fades in 0.2 s. It runs once per launch (the model lives in `AppController`), not when the window is opened again, and a launch at login cancels it. The dial's face reports its frame with `WindowFrameReporter`, an `NSView` that converts its bounds into the window's content view: SwiftUI's coordinate spaces don't reach across the split view's columns, which are hosted separately.

Things the user caught on 2026-11-01 that screenshots had shown and I had missed, keep them in mind when touching it. The toolbar (title, sidebar button and its glass) is drawn above any SwiftUI overlay, so `TitlebarHider` fades out everything visible in the window's titlebar view except the three standard window buttons while `hidesToolbar` is on, remembering each view's opacity, and gives exactly those values back (0.2 s) while the splash is still opaque, 0.15 s before the flight. Views AppKit keeps transparent are left alone, and the hider also gives the titlebar back when it leaves the window. Don't take toolbar items out instead (`.toolbar(removing: .sidebarToggle)`, tried first): a toolbar left empty is shorter, and the traffic lights jumped 10 pt when the items came back. Making only the button's view transparent left its glass platter (an `NSGlassEffectView` the glass container draws on its own) showing, and setting that view's alpha lost the icon for good. The flight measures the dial's face afresh before it starts (`measureDialFace`), since a reporter only reports when its own frame changes, not when an ancestor moves it; only that measure forces the window's layout (`layoutSubtreeIfNeeded`): the reports from `layout()`, `setFrameOrigin` and SwiftUI's updates convert the frame as last laid out, because the dial's reporter is updated on every tick and laying out the window there ran 10 times a second for the app's whole life; and the overlay's own origin is measured inside the `GeometryReader` that places the face (outside it, it started below the toolbar, which landed the face a toolbar's height too high). To check a landing, hold the splash for a couple of seconds after the flight in a temporary edit and compare a capture with one after it ends, or print the measured target and the dial's frame afterwards to stderr (stdout to a file is buffered and lost when the process is killed).

## Performance

Measured on 2026-11-01 on this Mac (M2 Pro, macOS 27.2), an optimized build with the Debug hooks (see below), at `-debugNow "2026-11-04 13:30"` with a 1500 USD salary, the window in front, CPU averaged over 15 s of `top`:

| | before | after |
|---|---|---|
| Earnings (Today) | 24 to 28% | 5 to 6% |
| Breakdown | 33 to 34% | 4 to 5% |
| window open, screen off | 9.6% / 24% | 0.2% |
| menu bar only | 0.4 to 0.7% | the same |

Where it went: the face's and the flying money's `TimelineView`s redrew the window 50 times a second, layout included (now Core Animation, see Face and splash); every tick re-evaluated the whole pane, the facts' Form and Breakdown's Form included (now `Equatable` parts, see Main window); the amount's interpolated `Text` resolved a localized string each tick; `TimeOfDay(parsing:)`'s regex ran four times a tick; and the earnings model stepped through the month's days up to eight times a tick (`businessDays` now counts them from the weekday the month starts on, tested against the stepping in `CalendarTests`, Santiago's midnight DST change included).

- Build what's measured with `xcodebuild … -configuration Release ARCHS=arm64 PRODUCT_BUNDLE_IDENTIFIER=com.nalezhytyi.millisalary.debug 'APP_DISPLAY_NAME=Millisalary Dev' SWIFT_ACTIVE_COMPILATION_CONDITIONS=DEBUG DEPLOYMENT_POSTPROCESSING=NO -derivedDataPath <elsewhere>`: optimized, with `-debugNow` and the other launch arguments, in the dev build's settings domain, symbols kept for `sample`. A Debug build's numbers are no guide, and the real Release build is the user's own settings domain.
- Launch it with `open -n -F <app> --args …` so the window comes to the front; started from the shell, it opens behind the frontmost app, its occlusion state says it's covered and the Ticker stops, which reads as a cheap pane. Check with a capture that the window shows, and that the screen is on: with the screen off or locked nothing ticks either.
- Memory (`footprint`) depends on the displays: the faces' frames are decoded for the sharpest one attached (until 2026-11-01 for the main one, so with a 1x external display as the main screen they took a quarter), and the CoreAnimation and malloc regions follow the window's backing stores, so a window on a 1x display takes less. Compare builds run one after the other on the same displays: on 2026-11-01, measured with frames for the 1x main display, the optimization left it where it was (Earnings 59 MB before and after, Breakdown 74 MB before and 70 MB after), while the same build measured 55 or 95 MB as the displays changed.

## Localization

English and Ukrainian (since 2026-11-01, `tasks/` has the plan). English is the source language: the keys of the two string catalogs are the English texts, so a text without a Ukrainian translation shows as its English key.

- **Two catalogs**: `Millisalary/Localizable.xcstrings` (the app) and `Packages/MillisalaryCore/Sources/MillisalaryCore/Localizable.xcstrings` (what the core makes: `Period.label`, `MenuBarContent`, `NotificationContent`; a resource of the package, `defaultLocalization: "en"`). `xcodebuild` doesn't add new texts to a catalog (only Xcode's editor does): add the key by hand, or `xcrun xcstringstool sync <catalog> --stringsdata <file>` from the target's `.stringsdata` under `build/DerivedData/Build/Intermediates.noindex/<target>.build` (the app target emits them with `SWIFT_EMIT_LOC_STRINGS`). A key with an interpolation is its format string: `"Day \(n) of 5, \(left) left today"` is `Day %lld of 5, %@ left today`; give positional arguments (`%1$@`) when a translation reorders them.
- **`scripts/check-localizations.swift`** fails on a text without a `translated` Ukrainian value, a plural without all four Ukrainian forms (one, few, many, other), and placeholders that don't match the key's. It compares placeholders with their argument numbers (`%1$@` twice and no `%2$@` fails) and fails on a `%` that starts none ("50 %": write `%%`). With a DerivedData folder it also fails on any text the code uses that a catalog lacks, reading each source file's newest `.stringsdata`, whichever configuration built it last. `build-dmg.sh` runs the first form. `"shouldTranslate": false` marks what is the same in every language ("–", "%@ %@").
- **What is localized**: `Text("…")`, `Section("…")`, `Label`, `Toggle`, `Picker`, `Button` and `LocalizedStringKey` parameters take a literal and look it up; a `String` variable shown in `Text(x)` does not (it is verbatim), so texts that are built (`WorkdayState.status`, `DialFact.title`, `Period.caption`, the status item's rows, the update alerts) are `String(localized: "…")` and shown as they are. `Text(verbatim:)` is for amounts, dates and names that are the same in every language.
- **Whole sentences**: each sentence is one key with its parts as arguments, never pieces put together in code, because Ukrainian moves the parts and inflects them ("Earning resumes on 2 December at 09:00" is "Наступний робочий день: 2 грудня, з 09:00", the colon keeping the weekday nominative, "…: понеділок, з 09:00", as `weekday(.wide)` gives no other case). The line under the dial is one key per line, its opening sentence included ("Day off. Earning resumes …": six of them), and is looked up again only when its inputs change (`StatusKey` in a `DayMemo`, at most once a minute), not on every tick. The link in the setup form is marked in its sentence as markdown (`[Settings](millisalary-settings:)`), for the same reason; the code turns that part into the accent colour and makes the whole sentence a plain `Button`, which takes keyboard focus (a link inside a `Text` doesn't). A plural variation must contain the number (Xcode refuses one that doesn't), so a text without it is two keys (`day left`, `days left`) or has none in a translation.
- **Dates and times** are formatted in `Locale.app`, never `Locale.current`: `Locale.autoupdatingCurrent` with its language replaced by the app's (`Locale.appLanguage`, from `Bundle.main.preferredLocalizations`, which `AppleLanguages`, the per-app setting and the translations in the bundle decide). `Locale.current`'s language is the first preferred one, which the app may not have: an English app on a Mac set to German first would name its days in German. It keeps the region and the Language & Region overrides (24-hour time, the first weekday): a first version built a locale from only the language and the region, and a US Mac with 24-hour time on read "until 5:00 PM". It's made on every use (about a microsecond), so a change of region or clock while the app runs shows on the next tick. Calendars the model makes stay Gregorian; only `calendar.locale = .app` is set, for the symbols (weekdays "пн…пт", months "січ…груд"). Payday's "10th" is the ordinal in English and the bare number in other languages ("10-го числа": the formatter's "10-ий" doesn't agree with the noun). Money is `formatCurrency`, always `uk_UA`.
- **Core's texts in tests**: `localized(_:_:)` takes a locale, which tests pass (`MenuBarContent(…, locale:)`, `NotificationContent(…, locale:)`, `Period.label(in:)`); with nil it uses the bundle's language, as the app does. `String(localized:bundle:locale:)` doesn't pick the language by `locale` (it only formats with it), hence `LocalizedStringResource`.
- **Terms**: Earnings = Заробіток, Breakdown = Деталі, At a Glance = Показники (renamed from Коротко, which read as unclear), Paycheck = Виплата, Payday = День виплати, Settings = Налаштування (the user agreed the glossary on 2026-11-01, then picked "Наступний робочий день: …" for when earning resumes, "до виплати", "Вже зароблено" and "лишилось" throughout). No long dash (—) in any text (the user's choice, 2026-11-02): a sentence is reworded instead ("Більше параметрів у налаштуваннях.", "У тебе найновіша версія Millisalary 0.3.0."), and a missing value is an en dash ("–"). The tone is conversational and addresses the user as «ти» throughout (the user's choice, 2026-11-02, over «ви»: "Перетягни позначений рядок…", "Показує твій заробіток…"; the setup form says "Кожна секунда приносить гроші"), without a gendered past tense, which «ти» would force: "Сьогодні зароблено %@.", not "Ти заробив".
- **Trying it**: `-AppleLanguages '(uk)'` on any launch (also `-AppleLocale uk_UA`; `-AppleLocale 'en_US@hours=h23'` is a US Mac with 24-hour time, since `-AppleICUForce24HourTime YES` as an argument doesn't reach `Locale.current`); `-NSShowNonLocalizedStrings YES` logs a text with no translation; `-NSDoubleLocalizedStrings YES` doubles every translated text, a stress test for layout (placeholders come out garbled in it, that's the doubling). `xcrun swift` with `LocalizedStringResource(…, bundle: .atURL(<app>))` and a `locale` prints a plural's forms for 1, 2, 5, 11, 21, 22.

## Notifications

`NotificationController` (notifications.ts). The Electron app's design, kept on purpose rather than handing notifications to the system ahead of time (`UNCalendarNotificationTrigger`): a check every 30 s (5 s tolerance, common run loop modes), on wake and on every settings change asks `NotificationTiming.due` what is due at `Clock.now`, sends it at once (`UNNotificationRequest` with no trigger, the key as its id, default sound) and stores the handled keys as `notificationsHandled` in the defaults. Every check compares with the settings of the previous one. When they changed (any edit, `defaults write` included), a due notification goes out only if the old settings had it due at the same time and the 30 s check just hadn't reached it; one the change itself made due is only marked handled: end of day or payday turned on after its time, End moved before now, a salary set after the end. This departs on purpose from the Electron app, which sent those at once, up to 3 h late. The first check at launch has no previous settings, so a launch after sleep still sends late ones within the grace. An edit that passes End through a time before now (stepping it down and back) uses up that day's key, as it did before. That way a late one past the 3 h grace is dropped instead of arriving hours later, nothing needs rescheduling when the settings, the rate or the clock change, and a Debug build's `-debugNow` drives it; the app is always running in the menu bar anyway. Amounts in the text go through `amountDisplay`, like the window's. Permission (`.alert`, `.sound`) is asked at launch when either notification is on (both are by default) and whenever one is turned on; `authorization` is refreshed when the app becomes active, and Settings shows a note and Open Notification Settings… (`x-apple.systempreferences:com.apple.Notifications-Settings.extension?id=<bundle id>`) when it's denied. The delegate (`ClickHandler`, set before launch finishes) shows the window on a click and shows banners while the app is in front. Logged under the `notifications` category, including each change of the authorization status (0 not determined, 1 denied, 2 authorized): System Settings' state can't be read from the shell on macOS 27 (`com.apple.ncprefs.plist` is no longer written).

## Open at login

`LoginItemController` (loginItem.ts). `launchAtLogin` registers or unregisters `SMAppService.mainApp`; at launch the setting follows the item's status (`.enabled` or `.requiresApproval` count as on), so removing the app in System Settings > General > Login Items turns the setting off. `loginItemRegistered` in the defaults remembers that the item has been in place: it's set when the status reads `.enabled` or `.requiresApproval` or after a successful register, and cleared after an unregister. At launch a setting that is on without an item turns off only when that flag says the item had been there (the user removed it); otherwise (the Electron import, `defaults write`, a register that failed) the app registers now, and tries again at every launch while that fails. A user who removed the item after their last 0.1.x launch gets it registered once more: that can't be told apart from the import. Only Release builds register (`isManaged`): a Debug build would leave a login item pointing into DerivedData, and Settings says so in Debug. `.requiresApproval` shows a note and Open Login Items Settings… (`SMAppService.openSystemSettingsLoginItems()`). Logged under `login-item`.

A launch at login starts with the menu bar item only: `AppDelegate.applicationWillFinishLaunching` calls `AppController.prepareLaunch`, which asks `wasLaunchedAtLogin` (only with the setting on): the launch Apple event's `keyAELaunchedAsLogInItem` where macOS still sets it, otherwise the Electron app's heuristic, the app's start within 90 s of this user's `loginwindow` (found with `NSRunningApplication`, whose `launchDate` is nil for it, and both start times read with `sysctl` `KERN_PROC_PID`). Then `Navigation.hideOnLaunch` makes `MainView` dismiss the window SwiftUI opens at launch (`dismissWindow` in `onAppear`). `.defaultLaunchBehavior(.suppressed)` would be cleaner but needs macOS 15, and `SceneBuilder` can't take an `if #available`. The Dock, a second launch and the menu bar item open the window as usual.

## Updates

`UpdateChecker` (updates.ts). 15 s after launch and then every 24 h it GETs `https://api.github.com/repos/<MillisalaryReleasesRepo>/releases/latest` (`Accept: application/vnd.github+json`) and reads it with `GitHubReleases.check`; a newer version than `CFBundleShortVersionString` is announced once through `NotificationController.announce` ("Millisalary 0.2.0 is available", "Click to open the download page."; its `userInfo` URL makes a click open the release page instead of the window), remembering it as `updateNotifiedVersion` in the defaults. Check for Updates… (after About in the app menu, before Quit in the menu bar item's) always answers in an `NSAlert`: the new version with Open Download Page / Later, "You're up to date", or "Couldn't check for updates". A click while a menu check's request or dialog is still out only brings the app forward, so dialogs don't stack. Debug builds don't check on their own unless `-debugReleasesURL` points them at a test server. Logged under `updates`.

## Menu bar item

`StatusItemController` shows a ring of today's working hours (`RingIcon`, a 16 pt template image the controller draws, so macOS tints it for the menu bar) with the amount as the button title in monospaced digits, refreshed by a 1 s timer (0.1 s tolerance) and immediately when the settings change (`withObservationTracking`). Before a salary is set it shows the ring alone, all faint. The menu lists This hour / Today / This week / This month / This year with their amounts (each opens Breakdown), a separator, Open Millisalary, Settings… (the Settings window), a separator and Quit Millisalary (⌘Q); without a salary the amount rows and their separator are left out. Titles and rows are only touched when their text changed, the menu is only rebuilt when the number of rows changes. `showInMenuBar` off hides the item.

The ring (`RingIcon`) is the Today dial's `DialScale(.day)`: one segment per clock hour from the one the workday starts in to the one it ends in (eight for 09:00–17:00, nine for 09:30–17:30, the first filled from its middle), filled up to the day's earned over total, the rest at 30% alpha, which a template image keeps. It's always today, whichever amount the title shows: a month's twenty-odd segments wouldn't read at 16 pt. Drawn with the dial's own `DialSegments` (radius 6, stroke 1.8, butt caps: round ones closed the gaps at this size, so it passes its own `gap`, 12° or 30% of a segment's angle, whichever is smaller). It's worked out on every refresh, before the title, so it turns over at midnight even when the title doesn't change, but the image is only drawn again when it moves: the fill is kept in steps of 1/150 of the ring, about half a pixel on a Retina screen, a step every three minutes or so of an eight-hour day.
