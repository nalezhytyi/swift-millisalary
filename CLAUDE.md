# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Millisalary, the app that shows your salary being earned in real time, rewritten natively in Swift for macOS. It replaces the Electron + React app in `../electron-millisalary` (~273 MB, most of it the Electron framework, and most of its UI work went into faking macOS controls in CSS). That app's `CLAUDE.md` is the behaviour spec: what isn't ported yet is described there. Treat `../electron-millisalary` as a read-only reference: never edit, build or commit there (reading it, or bundling its TypeScript into a temporary folder as the parity script does, is fine).

The user writes in Ukrainian: answer in Ukrainian. Code, comments, commit messages and this file stay in English.

## Commands

```bash
xcodegen generate                       # (re)generate Millisalary.xcodeproj from project.yml; after adding files too
xcodebuild -project Millisalary.xcodeproj -scheme Millisalary -derivedDataPath build/DerivedData build
xcodebuild -project Millisalary.xcodeproj -scheme Millisalary -derivedDataPath build/DerivedData test
swift test --package-path Packages/MillisalaryCore   # the same tests without Xcode, in seconds
open build/DerivedData/Build/Products/Debug/Millisalary.app
scripts/parity/generate-fixtures.sh     # regenerate the parity fixture from the Electron app's TypeScript
swift scripts/generate-icons.swift      # regenerate AppIcon and MenuBarIcon in the asset catalog from MoneyFace.png
scripts/build-dmg.sh                    # the universal Release app packed into build/Millisalary-<version>.dmg
scripts/release.sh                      # build the dmg and PUBLISH it as a GitHub release
```

- XcodeGen (`brew install xcodegen`, 2.46) is required: `Millisalary.xcodeproj` and `Millisalary/Info.plist` are generated and gitignored, `project.yml` is the source of truth (build settings, Info.plist keys, the package dependency, the scheme). Files in `Millisalary/` are picked up by folder, but only after `xcodegen generate`.
- Release: `-configuration Release`; the app is in `build/DerivedData/Build/Products/Release/` (~11 MB: Amplitude's SDK is about 5.7 MB of it, the face's animation 1.3 MB, the icon about 1 MB; the Release link warns once about an ambiguous atom inside `AmplitudeSwift.o`, the SDK's own code). It's universal (arm64 and x86_64: Xcode's default `ARCHS_STANDARD` with `ONLY_ACTIVE_ARCH = NO` for Release; `build-dmg.sh` builds for `generic/platform=macOS` and checks with `lipo`). `build-dmg.sh` makes a 3.5 MB dmg with the app and an Applications link (`hdiutil`, HFS+, UDZO), after `codesign --verify --deep --strict`.
- Never run `scripts/release.sh` without the user's explicit approval for that specific release: `gh release create` publishes. It refuses a dirty tree, a missing `origin` or one that isn't `MillisalaryReleasesRepo`, a `gh` account other than the repo's owner (two accounts are signed in here, a work one active by default: `gh auth switch --user nalezhytyi`), an existing tag and an unpushed HEAD, then tags `v<MARKETING_VERSION>` on HEAD and uploads the dmg with generated notes. Bump `MARKETING_VERSION` in `project.yml` first: it's the app's version (`CFBundleShortVersionString`) and the update check compares it with the latest tag. The README tells users how to open the unsigned app.
- Commit with the repo-local git identity (`nalezhytyi`, set in `.git/config`), not the global work identity. Conventional Commits with a lowercase scope, e.g. `feat(tray): …`, `feat(windows): …`, `fix(core): …`.
- There is no remote. Never create a GitHub repository, add a remote or push without the user's explicit approval for that specific action.

## Structure

- `Packages/MillisalaryCore/` — a local Swift package with everything that doesn't need AppKit or SwiftUI: the earnings model, settings schema, validation and edits, money formatting, the menu bar's text. Pure and unit-tested; the app depends on it (`packages:` in `project.yml`), and the scheme's test action runs its tests.
  - `Earnings.swift` — `EarningsModel` (`calculations.ts`): `earnings(at:_:)`, `workingWindow(on:_:)`, `isScheduledDay(_:workingDays:)`, `paydayInMonth(of:payday:)`, `nextPayday(from:payday:)`, plus `Period` (with `label`, "This hour" … "This year", the menu bar's and Breakdown's names), `EarningsSettings`, `WorkdaySettings`, `EarningsSnapshot`.
  - `Settings.swift` — `Settings` (`settings.ts`): the same 15 keys, values and defaults as the Electron app's `settings.json`; `Settings(sanitizing:)` / `applying(_:)` / `apply(_:for:)` are `sanitizeSettings` / `sanitizePatch` / one validator, `propertyList` is the way back, `workday` / `earningsSettings(exchangeRate:)` feed the model.
  - `SettingsEditing.swift` — the settings pane's edits with the coupled schedule fields (`settingsDraft.ts` and the `getNext*` helpers): `setStartHour` moves End by hours a day, `setEndHour` recomputes hours a day (an End before Start pulls Start back to it, and with no time between them hours a day fall back to 8, as in the Electron app), `setWorkingHoursPerDay` moves End, `setWorkingDays` / `setPayday` normalize.
  - `SalaryForm.swift` — `normalizeWorkingDays`, `normalizePayday`, `normalizeWorkingHoursPerDay`, `endHour(from:workingHoursPerDay:)` (`getEndHourFromStart`), `workingHoursPerDay(from:to:)` (`calculateWorkingHoursPerDayValue`) and the defaults (8 hours, 22 days).
  - `TimeOfDay.swift` — a wall-clock time; `TimeOfDay(parsing:)` / `formatted` are `parseTimeInputValue` / `formatTimeInputValue` for the `"HH:mm"` strings the settings keep.
  - `CurrencyFormat.swift` — `formatCurrency` (`uk_UA`, narrow symbol, plain spaces: `54 321,00 ₴`) and `formatCurrencyParts` (from the attributed format's number parts).
  - `MenuBarContent.swift` — the menu bar title and amount rows (`getTitle` / `getAmountLabels` in `tray.ts`).
  - `AnalyticsEvent.swift` — an event (snake_case name, string/number/bool properties) and `settingsChanges(from:to:)`, the Settings pane's events for an edit (getChangedFields plus settingsEvents.ts plus the pane's own).
  - `Updates.swift` — `ReleaseVersion` (`v1.2.3`, compared by number), `GitHubReleases.check(status:data:current:)` (`fetchLatest`'s reading of the API: 404 means no release yet, so current; the page URL must be https).
  - `ExchangeRate.swift` — `CurrencyPair` (`key` "USD>UAH", `Settings.ratePair`), `ExchangeRateAPI` (the URL, the response's rate with `fetchRate`'s checks, the 6 h refresh and the 1 min … 30 min retry delays) and `sanitizeRates` for the cached rates.
  - `Notifications.swift` — `EarningsModel.scheduledNotifications(around:settings:)` (`getScheduledNotifications`: the end of yesterday's and today's paid working windows, payday at the start time, keyed `end_of_day:2026-10-29` / `payday:…`), `NotificationTiming.due` (`check()`: once per key, a late one still sent for 3 h, the last 10 handled keys kept) and `NotificationContent` (Workday complete / It's payday).
- `Millisalary/` — the app target (Swift 6, default actor isolation `MainActor`).
  - `MillisalaryApp.swift` — the SwiftUI `App`: the main `Window` scene, the menu commands (`AppCommands`) and `AppDelegate` (Dock reopen, no quit on the last window).
  - `AppController.swift` — owns the store, `Navigation`, `Ticker` and the status item; `show(_ pane:)` / `showPeriod(_:)` are what every menu, the menu bar item and the Dock call (`showSection` in the Electron app). Applies the theme (`NSApp.appearance`) and runs the Electron import at launch.
  - `Navigation.swift` — `Pane` (earnings, breakdown, settings: window state, not a setting), `SidebarItem` (titles and SF Symbols), `Navigation` (`pane`, the split view's column visibility, `hideOnLaunch`, and `select(_:source:…)`, the one way a sidebar row gets selected, which reports it), `ActionSource` (sidebar, shortcut, tray, menu, button, setup_hint).
  - `SettingsStore.swift` — `@Observable`, one `UserDefaults.standard` value per settings key, always read through `Settings(sanitizing:)`; KVO on the keys picks up changes from anywhere, `defaults write` in Terminal included. `update(_:)` is `applySettingsPatch`: only the fields an edit changed, each through its validator (a rejected value keeps the stored one), and only those are written.
  - `ElectronSettingsImport.swift` — the one-time import, see Decisions.
  - `NotificationController.swift`, `LoginItemController.swift`, `UpdateChecker.swift`, `Analytics.swift` — see Notifications, Open at login, Updates and Analytics.
  - `ExchangeRateStore.swift` — `@Observable`, the rate for the pair the settings name (see Exchange rate); `AppController` points it at `store.settings.ratePair` and refreshes it on wake.
  - `Settings+App.swift` — `AmountDisplay` (currency and rate) from `amountDisplay(_ rates:)`, and `earnings(at:_:)`: every amount on screen goes through these two.

  - `StatusItemController.swift` — the menu bar item, see below.
  - `Views/` — `MainView` (the `NavigationSplitView` and its sidebar), `EarningsView` (the dial, the stats row, the setup hint), `BreakdownView`, `SettingsView`.
  - `FaceAnimation.swift` — the face's frames and clock, and `MoneyFace`, the view every animated face uses; `Views/Splash.swift` — `SplashModel`, `SplashView` and `WindowFrameReporter`. See Face and splash.

## The port and its parity

The Swift core must give the Electron app's results, so the TypeScript is the oracle. `generate-fixtures.sh` bundles `fixtures.ts` with the esbuild in `../electron-millisalary/node_modules/.pnpm/esbuild@*/` (aliasing `@shared` and `@renderer` to its `src/shared` and `src/renderer/src`, resolving `dayjs` from its `node_modules`) into a temporary folder and runs it with node. The fixture holds 2610 `calculateEarnings` / `getWorkingWindow` / `isScheduledDay` results (15 schedules: overnight, no end time, same start and end, fractional hours and days, 24-hour days, a rate, no salary; at edge instants plus 20 seeded random ones over 2026–2028; in Europe/Kyiv, America/New_York and Asia/Kolkata), every payday 1–31 for 13 months, 256 `formatCurrency` and 256 `formatCurrencyParts` results (8 currencies, 2 and 4 digits, half-way amounts), 174 coupled-field edits (`withStartHour` / `withEndHour` / `withWorkingHoursPerDay` / `withWorkingDays` / `withPayday` on 6 schedules, times anchored to a day without a DST change), 176 `getScheduledNotifications` results (8 settings, 11 instants, Kyiv and New York), the normalizers (NaN and the infinities included), time strings and 22 raw settings objects through `sanitizeSettings`. `ParityTests.swift` compares money **exactly**, not with a tolerance. The fixture is committed, so the tests don't need node; regenerate it only when the reference changes, and keep the edge cases.

What makes the results equal to the bit, keep it when changing the core:

- Times are whole milliseconds as `Double`, like a JS `Date` (`epochMilliseconds`); `earnings(at:)` rounds `now` to a millisecond first. The arithmetic runs in the TypeScript's order (`millisecondSalary * 3600 * 1000`, not `* 3_600_000`).
- Each dayjs call maps to a `Calendar` call in the model's calendar (its time zone stands in for the local one): `startOf('day' | 'month' | 'hour')`, `add(n, 'day')` keeps the wall-clock time, `day()` is 0 for Sunday, `diff(…, 'day')` corrects for a change of UTC offset and truncates.
- `atMinutes` mirrors `startOf('day').hour(h).minute(m)`: the hour can run past 23 into the next day (a missing end time is start + hours/day, e.g. 20:00 + 9.5 h is 05:30 next morning) and fractional minutes are truncated (09:00 + 8.33 h ends at 17:19, not 17:19:48). When the end isn't after the start, the end is start + hours/day in milliseconds, truncated like a JS `Date`. `endHour(from:)` adds the same truncated milliseconds.
- `workingDays` is a `Double` and stays fractional (the Electron validator doesn't round it); `payday` is an `Int` (it does).
- `formatCurrency` rounds half away from zero (`.toNearestOrAwayFromZero`), as `Intl.NumberFormat` does; Foundation's default is half-even. Both format the shortest decimal of the double, so `1.005` gives `1,01`.
- The validators treat an `NSNumber` boolean as not a number and a number as not a boolean (`CFBooleanGetTypeID`), like `typeof`.
- Read JSON numbers with `JSONDecoder`, not `JSONSerialization`: the latter returns long decimals as `NSDecimalNumber`, whose `doubleValue` is off in the last bits (it broke the first test run). The Electron import has to take untyped JSON for the validator, so it converts any `NSDecimalNumber` through its exact text.
- Not covered: a start or end time inside a DST gap or overlap (03:00–04:00 in Kyiv on the last Sundays of March and October). JS moves a missing local time forward and picks the first of a repeated one; `Calendar` may differ. Those are Sundays, which aren't paid, so only `rates` could differ. The coupled fields are wall-clock in Swift, where the Electron app adds hours to a `Date` of today, so on a DST day its End could come out an hour off; the Swift one doesn't.

## Decisions

Taken on 2026-10-31 and 2026-11-01; "the user's choice" marks what the user picked between options.

- **XcodeGen** over a hand-made `.xcodeproj` or SwiftPM with a bundling script (the user's choice): a readable, diffable spec that `xcodebuild` builds, with asset catalogs, Info.plist keys and SPM dependencies (Sparkle later) handled by Xcode.
- **macOS 14** deployment target (the user's choice): `@Observable`, `SettingsLink`, `SMAppService`, `MenuBarExtra`, `@Environment` with observable types. Newer APIs (Liquid Glass, `glassEffect`, `toolbarBackgroundVisibility`, macOS 15/26) go behind `if #available`; on newer systems the native look comes by itself. Built with Xcode 27.2 / macOS 27.2 SDK / Swift 6.4.
- **Swift Testing** for tests. Swift 6 language mode; the app target uses `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` and approachable concurrency, so app code is main-actor by default (`DefaultsObserver` opts out with `nonisolated`). The core's `Settings` clashes with SwiftUI's `Settings` scene: write `MillisalaryCore.Settings` in SwiftUI files.
- **Bundle IDs**: Release is `com.nalezhytyi.millisalary`, the Electron app's, so the native app is its successor (same login item and notification identity, installs over it). Debug is `com.nalezhytyi.millisalary.debug`, so a dev build never shares settings, notifications or the login item with an installed copy, and it's named "Millisalary Dev" (`APP_DISPLAY_NAME`, `CFBundleName` and `CFBundleDisplayName`): with both called Millisalary, the user allowed notifications for the installed one in System Settings instead of the dev build (2026-11-01).
- **Signing**: ad hoc (`CODE_SIGN_IDENTITY = -`) with the hardened runtime, not notarized; there is no Developer ID. Not sandboxed, like the Electron app (no App Store, and a sandbox would keep the app from reading the Electron app's `settings.json`).
- **Settings in UserDefaults**, one value per key under the `settings.json` names, rather than a JSON file: native, inspectable with `defaults read`, editable with `defaults write`. Everything read goes through the ported validator, every edit through `SettingsStore.update`.
- **The main window is a SwiftUI `Window` scene**, not an AppKit `NSWindow` hosting SwiftUI. The hosted version was built first and dropped the same day: with `NSHostingController` (even with `sceneBridgingOptions = .all`) the `NavigationSplitView` got no toolbar, no sidebar button and no navigation title, and the sidebar drew the old flat way. In a `Window` scene macOS 27 draws it natively: the title is the selected row's name, the sidebar button is the glass circle next to the traffic lights. The cost: AppKit code can't open a scene, so `AppCommands` hands its `@Environment(\.openWindow)` to `AppController.openWindow` while the commands are built (at launch, window open or not), and `show(_:)` calls it, which opens the window or brings it to the front. Closing the window closes it (SwiftUI keeps the `NSWindow` and reuses it), unlike the Electron app's hide-on-close: a native window is cheap to bring back, and nothing ticks while it's closed. `NSWindow.allowsAutomaticWindowTabbing = false`: one window, no tab items in the menus.
- **Always in the Dock** (the user's choice), like the Electron app: closing the window leaves the app in the Dock and the menu bar; a Dock click or a second launch reopens it (`applicationShouldHandleReopen`). `showInMenuBar` hides the menu bar item (`isVisible`).
- **Settings shows only what works** (the user's choice), which since 2026-11-01 is everything the Electron app had: Salary (amount, salary and display currency), Schedule, Payday, General (Open at login), Notifications, Menu bar, Appearance. Native controls throughout (a grouped `Form`, `Picker` pop-ups with the current value added when it isn't a choice, e.g. 8.33 hours, `DatePicker` hour-and-minute fields on a fixed day without DST, a `TextField` with a number format that commits on Return or when focus leaves, as native fields do, rather than on every keystroke like the Electron one).
- **The app icon is the Electron app's** (the user's choice over a Liquid Glass `.icon` from Icon Composer): `scripts/generate-icons.swift` is its generator ported (the face mapped onto a rounded square with the elliptical grid mapping, on the 824-of-1024 icon grid with a soft shadow), pixel-identical to the Electron icon at 1024 px; the menu bar template icon comes out byte-identical.
- **The launch splash is ported** (the user's choice, against my recommendation to drop it, since native apps open at once and Apple advises against splash screens). See Face and splash.
- **The Electron settings are imported automatically** (the user's choice), once: on the first launch, if nothing is stored here yet, from the newest of `~/Library/Application Support/{Millisalary,electron-millisalary}/settings.json`, through the validator, with its cached `exchangeRates` (through `sanitizeRates`; rates already known here win); the file is only read. `didImportElectronSettings` in the defaults marks the attempt, whether or not there was a file.
- **NSStatusItem**, not SwiftUI's `MenuBarExtra`: the title needs `monospacedDigitSystemFont` (like Electron's `fontType: 'monospacedDigit'`), and an AppKit menu can update its rows while open (the timer runs in the run loop's common modes, so the amounts tick inside the open menu, which the Electron app couldn't do: it only rebuilt its menu while closed).
- **Updates as in the Electron app** (the user's choice over Sparkle, which would install updates itself but needs an EdDSA key in the user's Keychain and an appcast published with every release): a check of the latest GitHub release that only points to its page. Releases go to `nalezhytyi/swift-millisalary` (`MillisalaryReleasesRepo` in `project.yml`), a repository that doesn't exist yet: creating it, adding the remote and pushing need the user's go-ahead. One universal dmg rather than the Electron app's one per architecture: the native binary is small.
- **Analytics through Amplitude's Swift SDK** (the user's choice over a hand-written client), into **the Electron app's Amplitude project** (its client key, the user's choice), with its event names, and **`salary_input_blurred` carries the salary amount** as it did there (the user's choice, against my recommendation to send only `has_salary_value`). No Session Replay: Amplitude's requires "Your application runs on iOS or iPadOS" (its docs, checked 2026-11-01). `Amplitude-Swift` is pinned with `exactVersion` in `project.yml` (1.19.4, with AmplitudeCore-Swift 1.6.1 and analytics-connector-ios).
- **Until a pair's rate is known, amounts stay in the salary's currency** (rate 1, the salary currency's symbol), e.g. on a first launch without network; Breakdown's footer says so. The Electron app multiplied by 1 and showed the display currency's symbol meanwhile, which put wrong numbers on screen.
- Small deliberate differences from the Electron app: amounts tick in monospaced digits in the dial, the stats row and Breakdown (no jitter at 10 updates a second); the payday date and the number pickers follow the system's region format (e.g. "Tuesday, 10 November" on an en_UA Mac, where dayjs always wrote "Tuesday, November 10"); the setup hint's button says "Open Settings" (title case, as macOS buttons do).

## Main window

One `Window` (820×580 by default, at least 520×460, its frame kept by SwiftUI) with a `NavigationSplitView` (sidebar 180–360 pt, 240 by default). The sidebar has an Earnings section with This Hour, Today, This Week, This Month and This Year, then Breakdown and Settings, each with an SF Symbol. Picking a period sets the `selectedPeriod` setting and shows the Earnings pane; the pane itself is window state (`Navigation.pane`). The navigation title is the selected row's name.

- **Earnings**: the dial (the Electron SVG's proportions: a ring of radius 44 and stroke 6 in 100, the track in `.quaternary`, the arc in the accent colour from the top, grown in over 0.7 s when it appears and when the period changes, the 100 ms ticks applied directly in between, nothing under Reduce Motion), the face at 16% of its width, the amount with its last two of four decimals at 62% in the secondary colour and the symbol at 70% in the accent colour, sized to fit like the Electron app's estimate, and "of <total> <today/this week/…>"; under it the stats row (Today, This week, This month) or, with no salary, the setup hint with a button to Settings. Its toolbar has no background (`toolbarBackground(.hidden)`), since nothing scrolls under it there.
- **Breakdown**: a grouped `Form`: the next payday card (face, date, paycheck, days left), Earned so far (each period's amount, total and a progress bar), Your rate (per second with four decimals, minute, hour, day) and its footer, which adds "Exchange rate: 1 USD = 45,4 UAH." when the currencies differ, or that amounts are in the salary currency until the rate arrives.
- **Settings**: see Decisions; every change applies at once.
- The `Ticker` drives both live panes at 100 ms; only views that read `ticker.now` redraw.

The app menu (`AppCommands`): Settings… ⌘, in the app menu; in View, Toggle Sidebar ⌃⌘S, This Hour … This Year ⌘1–⌘5 as checkmarked items that follow the selected period, and Breakdown ⌘I. The rest is SwiftUI's and AppKit's standard (Edit, Window with the window listed, Help). Check for Updates… comes with the updater.

## Exchange rate

`ExchangeRateStore` (exchangeRate.ts in the Electron app). `follow(pair)` runs at launch and whenever a currency changes (an `withObservationTracking` loop in `AppController`; other setting changes don't refetch): the same currency is always 1; otherwise the cached rate for the pair at once (nil when there is none) and a fetch of `https://api.exchangerate-api.com/v4/latest/<FROM>` with `URLSession`, whose `rates[<TO>]` must be a finite number above 0, and a non-2xx status is a failure too. One `Task` per pair loops: after a fresh rate it sleeps 6 h, after a failure 1 min, doubling up to 30 min; following another pair cancels it, and a result for a pair no longer followed is dropped. `refresh()` on `NSWorkspace.didWakeNotification` fetches again at once. Each fresh rate is cached in the defaults as `exchangeRates`, a dictionary of `Double`s keyed like "USD>UAH" (read through `sanitizeRates`), so an offline launch keeps converting. `rate(for:)` only returns the followed pair's rate. Fetches and failures are logged under the `exchange-rate` category of the bundle ID's subsystem (no amounts, only pairs and rates).

## Face and splash

`FaceAnimation` (owned by `AppController`) holds the frames of `money-face.webp`, decoded with ImageIO at the largest size a face is shown at (the splash's 96 pt × the screen scale: 192 px, about 20 MB, 0.2 s), and one clock (`epoch`): every `MoneyFace` shows frame `elapsed / 20 ms mod 150` through a `TimelineView(.animation)`, so the splash's face and the dial's show the same frame, which is how the browser's one clock per image behaved in the Electron app. ImageIO's own player (`CGAnimateImageDataWithBlock`) does play WebP but took 3.7 s for the 3 s cycle, hence the own clock. `MainView` loads the frames when the window appears and drops them when it closes; frame 0 is decoded at once and the rest in the background. Until they're ready a face shows frame 0, not `MoneyFace.png`: the still picture is a different, glossier drawing (the animation is a cartoon one, smaller in its square), so switching from it would jump. Under Reduce Motion `MoneyFace` is the still picture, as the Electron app's `<picture>` was. The payday card in Breakdown always shows the still picture, as there. Memory (`footprint`): 32 MB with only the menu bar item, 83 MB with the window open and the face animating (Debug build, 2026-11-01).

The splash (`SplashModel`, splash.ts in the Electron app) is an overlay over the whole `NavigationSplitView`, sidebar and toolbar included, in the detail pane's colour (`textBackgroundColor`: white, or #1e1e1e dark), with the face at 96 pt in the middle. Once every frame is decoded it restarts the face's clock and plays one 3 s cycle (a click skips the rest); then, if the window is on an Earnings pane and the dial's face has reported its frame (within 2 s), the face flies onto it in 0.5 s on `timingCurve(0.32, 0.72, 0, 1)` while the background fades out in 0.3 s, and the dial's own face, hidden until then, takes over on the same frame. Otherwise (Breakdown or Settings, no dial) and under Reduce Motion (the still face for 0.8 s) the splash fades in 0.2 s. It runs once per launch (the model lives in `AppController`), not when the window is opened again, and a launch at login cancels it. The dial's face reports its frame with `WindowFrameReporter`, an `NSView` that converts its bounds into the window's content view: SwiftUI's coordinate spaces don't reach across the split view's columns, which are hosted separately.

Three things the user caught on 2026-11-01 that screenshots had shown and I had missed, keep them in mind when touching it: the toolbar (title, sidebar button) is drawn above any SwiftUI overlay, so `hidesToolbarItems` takes them out (`.toolbar(removing: .sidebarToggle)`, an empty `navigationTitle`) while the splash covers the window, leaving only the traffic lights as in the Electron app; putting them back makes the toolbar taller and moves the content down ~10 pt, so they come back while the splash is still opaque, the flight waits 0.15 s and then measures the dial's face afresh (`measureDialFace`: a reporter only reports when its own frame changes, not when an ancestor moves it, so the old report would have landed the face 10 pt too high); and the overlay's own origin is measured inside the `GeometryReader` that places the face (outside it, it started below the toolbar, which landed the face a toolbar's height too high). To check a landing, hold the splash for a couple of seconds after the flight in a temporary edit and compare a capture with one after it ends, or print the measured target and the dial's frame afterwards to stderr (stdout to a file is buffered and lost when the process is killed).

## Notifications

`NotificationController` (notifications.ts). The Electron app's design, kept on purpose rather than handing notifications to the system ahead of time (`UNCalendarNotificationTrigger`): a check every 30 s (5 s tolerance, common run loop modes), on wake and on every settings change asks `NotificationTiming.due` what is due at `Clock.now`, sends it at once (`UNNotificationRequest` with no trigger, the key as its id, default sound) and stores the handled keys as `notificationsHandled` in the defaults. That way a late one past the 3 h grace is dropped instead of arriving hours later, nothing needs rescheduling when the settings, the rate or the clock change, and a Debug build's `-debugNow` drives it; the app is always running in the menu bar anyway. Amounts in the text go through `amountDisplay`, like the window's. Permission (`.alert`, `.sound`) is asked at launch when either notification is on (both are by default) and whenever one is turned on; `authorization` is refreshed when the app becomes active, and Settings shows a note and Open Notification Settings… (`x-apple.systempreferences:com.apple.Notifications-Settings.extension?id=<bundle id>`) when it's denied. The delegate (`ClickHandler`, set before launch finishes) shows the window on a click and shows banners while the app is in front. Logged under the `notifications` category, including each change of the authorization status (0 not determined, 1 denied, 2 authorized): System Settings' state can't be read from the shell on macOS 27 (`com.apple.ncprefs.plist` is no longer written).

## Open at login

`LoginItemController` (loginItem.ts). `launchAtLogin` registers or unregisters `SMAppService.mainApp`; at launch the setting follows the item's status (`.enabled` or `.requiresApproval` count as on), so removing the app in System Settings > General > Login Items turns the setting off. Only Release builds register (`isManaged`): a Debug build would leave a login item pointing into DerivedData, and Settings says so in Debug. `.requiresApproval` shows a note and Open Login Items Settings… (`SMAppService.openSystemSettingsLoginItems()`). Logged under `login-item`.

A launch at login starts with the menu bar item only: `AppDelegate.applicationWillFinishLaunching` calls `AppController.prepareLaunch`, which asks `wasLaunchedAtLogin` (only with the setting on): the launch Apple event's `keyAELaunchedAsLogInItem` where macOS still sets it, otherwise the Electron app's heuristic, the app's start within 90 s of this user's `loginwindow` (found with `NSRunningApplication`, whose `launchDate` is nil for it, and both start times read with `sysctl` `KERN_PROC_PID`). Then `Navigation.hideOnLaunch` makes `MainView` dismiss the window SwiftUI opens at launch (`dismissWindow` in `onAppear`). `.defaultLaunchBehavior(.suppressed)` would be cleaner but needs macOS 15, and `SceneBuilder` can't take an `if #available`. The Dock, a second launch and the menu bar item open the window as usual.

## Updates

`UpdateChecker` (updates.ts). 15 s after launch and then every 24 h it GETs `https://api.github.com/repos/<MillisalaryReleasesRepo>/releases/latest` (`Accept: application/vnd.github+json`) and reads it with `GitHubReleases.check`; a newer version than `CFBundleShortVersionString` is announced once through `NotificationController.announce` ("Millisalary 0.2.0 is available", "Click to open the download page."; its `userInfo` URL makes a click open the release page instead of the window), remembering it as `updateNotifiedVersion` in the defaults. Check for Updates… (after About in the app menu, before Quit in the menu bar item's) always answers in an `NSAlert`: the new version with Open Download Page / Later, "You're up to date", or "Couldn't check for updates". Debug builds don't check on their own unless `-debugReleasesURL` points them at a test server. Logged under `updates`.

## Analytics

`Analytics` (amplitudeClient.ts, `@Observable` only to be in the SwiftUI environment) wraps `Amplitude` with `autocapture: .sessions` (on macOS the SDK has no app lifecycle events: its `MacOSLifecycleMonitor` only drives sessions; `.appLifecycles` was tried and sent nothing), `enableDiagnostics: false` and `enableAutoCaptureRemoteConfig: false` (both default to on and would talk to Amplitude's diagnostics and config servers). Release builds send to Amplitude's default endpoint every 30 s; Debug builds send nothing unless `-debugAnalyticsURL <url>` points them at a test server (then every 2 s). The SDK fills in `device_id`, `session_id`, `platform` "macOS", `os_name`/`os_version`, `version_name` (the bundle's short version, not `app_version`) and `library`; `ip` is resolved by Amplitude.

The events, as the Electron app sent them: `sidebar_item_selected {item, source}` and `period_changed {period, source}` from `Navigation.select` (sources: sidebar, shortcut for ⌘, / ⌘I / ⌘1–⌘5, tray for the menu bar item's rows and Settings…, setup_hint, and `menu` for the period itself when it comes from the View menu), `sidebar_toggled {visible, source}` (shortcut for ⌃⌘S; SwiftUI's sidebar button and dragging the sidebar shut both report `button`, they can't be told apart), the Settings pane's events through `SettingsView.update` and `AnalyticsEvent.settingsChanges` (only edits made there, not `defaults write` or the import; `workday_start_time_changed`, `workday_end_time_changed` and `working_hours_per_day_changed` go out 1.5 s after the last change, so stepping a time field sends one, where the Electron app waited for the field's blur), `tray_menu_opened` (the status menu's `menuWillOpen`), `notification_clicked {kind}` and `update_notification_clicked {version}` (from the notification's id, "end_of_day:…", "payday:…", "update:<version>"), `update_check_clicked {source: menu | tray}` and `update_available_notified {version}`. Not sent: `sidebar_resized` (a `NavigationSplitView` doesn't report its width), and the browser's autocaptured page views and clicks.

## Menu bar item

`StatusItemController` shows the template icon (`MenuBarIcon` in `Assets.xcassets`, the Electron app's `trayTemplate.png` / `@2x`, 16 pt) with the amount as the button title in monospaced digits, refreshed by a 1 s timer (0.1 s tolerance) and immediately when the settings change (`withObservationTracking`). Before a salary is set it shows the icon alone. The menu lists This hour / Today / This week / This month / This year with their amounts (each opens Breakdown), a separator, Open Millisalary, Settings…, a separator and Quit Millisalary (⌘Q); without a salary the amount rows and their separator are left out. Titles and rows are only touched when their text changed, the menu is only rebuilt when the number of rows changes. `showInMenuBar` off hides the item.

## Testing

- `swift test --package-path Packages/MillisalaryCore` runs the parity and unit tests (29, under a second); `xcodebuild … test` runs the same through the scheme. There are no UI tests: the app is checked by running it.
- The dev build keeps its settings in the `com.nalezhytyi.millisalary.debug` domain. On its first launch it imports the Electron app's settings (the user's real salary): don't quote those amounts back. `defaults write com.nalezhytyi.millisalary.debug monthlySalary -float 54321` (and `menuBarAmount selected`, `selectedPeriod year`, `theme light`, …) changes a running app within a second; `defaults delete com.nalezhytyi.millisalary.debug` resets it, `defaults delete com.nalezhytyi.millisalary.debug didImportElectronSettings` together with the settings keys makes the next launch import again. Put back what you changed when you're done.
- Debug-only launch arguments (read through the UserDefaults argument domain, compiled out of Release):
  - `-debugNow "2026-10-29 13:30"` starts the clock at that local time and lets it run, so a weekend can show a weekday ticking (weekends earn nothing). It's a date and not an offset because a negative offset (`-debugTimeShift -205200`, tried first) was ignored: a value starting with `-` reads as another flag.
  - `-debugPane earnings|breakdown|settings` opens the window on that pane.
  - `-debugDumpMenus <path>` writes the app menu and the menu bar item's menu as text a second after launch (titles, shortcuts, `[on]`, `[disabled]`, `[hidden]`). The status menu's rows carry amounts.
  - `-debugStatusItemSnapshot <path.png>` draws the menu bar button into a PNG on every title change.
  - `-debugAnalyticsURL <url>` sends a Debug build's analytics there.
  - `-debugReleasesURL <url>` makes a Debug build check that URL for the latest release, on its own too.
  - `-debugLaunchedAtLogin YES` starts as if the system had started the app at login (no window).
  - `-debugExchangeRateURL <base>` sends the rate requests elsewhere; `http://127.0.0.1:9/` (nothing listens) shows the offline behaviour and the retries.

## Not ported yet

Everything in the Electron app's `CLAUDE.md` is ported, except what has no native counterpart: Session Replay (Amplitude's is iOS-only), the `sidebar_resized` event and the sidebar's custom resizing and its 640 pt auto-hide (`NavigationSplitView` does its own), and the Electron-specific plumbing (IPC, preload, CSP, the renderer's lazy chunks).
